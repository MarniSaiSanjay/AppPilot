AppPilot

A goal-driven AI agent for Android regression testing — it drives a real app by reasoning over the live UI, not by running a fixed script.

Setup & usage — everything you need to run it

What is AppPilot?

Give AppPilot a test goal and a running Android emulator, and it drives the target app toward that goal by reasoning over the live UI hierarchy. It runs a simple loop: 

observe the UI → is the goal reached? → ask the model for one action
→ validate it for safety → execute it via Maestro → observe again → repeat

Login completion uses deterministic terminal/blocker evidence first and semantic classification only for ambiguous screens. Deeplink PASS remains owned by the separate result judge. The run reaches PASS when its authoritative evaluator recognizes the goal state, and FAIL when it cannot safely proceed or an action limit is hit. Unexpected screens (permission prompts, "save password" dialogs, onboarding pages) are handled by reasoning, not by pre-scripting every screen.

The roles: the LLM is the brain (chooses the next action), the Android UI hierarchy is the eyes, Maestro is the hands (execution only), and the test goal is the objective. The prototype targets the Office hub app com.microsoft.office.officehubrow.

1Prerequisites

Make sure you have all of these before you start:

  • macOS or Linux with a terminal (commands below assume macOS/zsh).
  • Python 3.11+ — AppPilot uses only the standard library, so there are no pip packages to install.
  • Java 17+ (JDK) — required by Maestro.
  • Maestro CLI — the tool that actually taps/types on the device.
  • Android SDK platform-tools (gives you adb) and an Android emulator (or a physical device).
  • For the standalone login CLI, the target app installed on the device. The deeplink suite manages its local APK installation.
  • An OpenAI-compatible LLM endpoint — a model name/deployment and an API key.
Quick version checks 
python3 --version   # 3.11 or newer
java -version       # 17 or newer
adb --version       # from Android SDK platform-tools

2Install & setup

  1. Clone the repository

    git clone https://github.com/MarniSaiSanjay/AppPilot.git
cd AppPilot

  2. Install the Maestro CLI

    Maestro needs Java 17+. On macOS:

    curl -fsSL "https://get.maestro.mobile.dev" | bash
# add Maestro to your PATH (zsh shown; use ~/.bashrc for bash)
echo 'export PATH="$HOME/.maestro/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
maestro --version

  3. Make sure adb is available

    Installed with Android Studio (or the standalone platform-tools). If adb is not found, add the SDK to your PATH, e.g.: 

    export ANDROID_HOME="$HOME/Library/Android/sdk"
export PATH="$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$PATH"

  4. Create your .env file

    See Configuration below — this holds your model settings and (optionally) sign-in credentials. It is git-ignored, so nothing secret is ever committed.

No dependency install step AppPilot's Python code is standard-library only — there is nothing to pip install. If you want an isolated interpreter you can still create a virtualenv (python3 -m venv .venv && source .venv/bin/activate), but it is optional.

3Configuration

AppPilot reads all configuration from environment variables. A git-ignored .env file at the repo root is loaded automatically at startup (real environment variables always win, and nothing secret is committed).

VariableRequiredPurpose
APPPILOT_MODELYesDecision-model deployment/name (e.g. gpt-4.1-mini).
APPPILOT_MODEL_API_KEYYesAPI key for the model endpoint.
APPPILOT_MODEL_BASE_URLNoOpenAI-compatible base URL (defaults to the OpenAI v1 endpoint).
APPPILOT_USERNAMEFor loginSign-in username/email for the app under test (e.g. the Microsoft account used to log into the Office hub app) — resolved locally and injected straight into Maestro, never sent to the model. Not the model API key.
APPPILOT_PASSWORDFor loginSign-in password for the app under test — handled the same secure way.
APPPILOT_MAX_ACTIONSNoUpper bound on actions per run (default 30).
APPPILOT_MAX_STUCK_ACTIONSNoConsecutive no-change actions before a controlled early FAIL (default 5).

Example .env

APPPILOT_MODEL=gpt-4.1-mini
APPPILOT_MODEL_API_KEY=your-key-here
APPPILOT_MODEL_BASE_URL=https://your-endpoint.openai.azure.com/openai/v1
APPPILOT_USERNAME=you@example.com
APPPILOT_PASSWORD=your-password
Credentials stay secret Credentials are never placed in prompts, observations, logs, exceptions, Maestro arguments, or source. The model can only request a credential by kind (username/password); AppPilot resolves the real value locally and hands it to Maestro securely.
These are the app's login credentials APPPILOT_USERNAME / APPPILOT_PASSWORD are the sign-in credentials for the app being tested (the account AppPilot signs in with when a scenario reaches a login screen). They are only needed for login scenarios, and are unrelated to the model API key (APPPILOT_MODEL_API_KEY) or any GitHub credentials.

4Start the emulator

Launch an Android emulator (from Android Studio → Device Manager, or the terminal), then confirm it is connected. The standalone login CLI requires the target app to be installed; the deeplink suite manages its local APK installation.

adb devices
# expected output, e.g.:
# List of devices attached
# emulator-5554   device

Note the device id (e.g. emulator-5554) — you pass it with --device below.

5Run the agent

With the emulator running and .env in place:

python3 src/apppilot_agent.py --device emulator-5554

Options

FlagMeaning
--deviceADB device id (default emulator-5554).
--max-actionsOverride the absolute per-run action bound.
--max-stuck-actionsOverride the early-termination "stuck" bound.
--guidanceOverride the default high-level guidance given to the model.

The run prints the loop explicitly, so you can follow exactly what it does:

GOAL
OBSERVE
MODEL DECISION
SAFETY VALIDATION
ACTION
OBSERVE
GOAL REACHED
RESULT

The current prototype goal: complete authentication & onboarding and reach a usable signed-in Microsoft 365 Copilot experience, without executing an unintended suggested prompt.

6Deeplink test suite

A data-driven runner (src/deeplink_runner.py) executes a suite of deeplink test cases from an Excel workbook, reusing the same Maestro executor, UI observer, and model config as the agent. 

python3 src/deeplink_runner.py --device emulator-5554

The workbook

Four required fields plus an optional Installed field. Recognized headers may be reordered; without a header the required fields use columns A-D. Test suites live in testcases/deeplinks/ (for example deeplink_tests.xlsx).

ColumnMeaning
Test IDIdentifier for the case.
Deep LinkThe exact deeplink URI to launch (used verbatim).
User TypeThe user/scenario the case targets.
Expected ResultA natural-language description of the expected outcome.
Installed (optional)Selects installed versus genuine fresh-install execution. When omitted, AppPilot derives it from the deeplink.

How each case runs

  1. Installed cases are prepared as one batch: install/launch, login, then one warm-up for the batch.
  2. Uninstalled cases recreate uninstall → exact deeplink while absent → local APK install/open → login for every attempt. They never warm up.
  3. The resulting Android UI is observed and polled for a bounded verification window.
  4. The AI judge owns deeplink PASS/FAIL by comparing the UI with Expected Result.
  5. Installed retries stop/wait/reopen. Uninstalled retries recreate the full fresh-install sequence. The default is 2 attempts.

Options

FlagMeaning
--excelExplicit workbook path. Omit to run the only suite in testcases/deeplinks/, or to pick from a menu when several exist.
--deviceADB device id.
--max-attemptsAttempts per case before FAIL (default 2).
--verify-timeoutBounded polling window for the expected result (default 30 seconds).
--no-warm-upSkip the one-time installed-batch warm-up.
--apkPath to the local .apk to install (else the saved path is offered/reused, otherwise you are prompted).

At the end it prints a concise per-test report plus totals (Total / Passed / Failed).

Local APK and deferred-link requirements AppPilot installs only a user-provided local .apk — there is no build, enlistment, or store acquisition. Supply it with --apk PATH or let the CLI offer the saved path (.apppilot_apk, gitignored) / prompt for one at startup; it is validated (exists, is a file, .apk, readable) before the suite runs, and an invalid path exits with code 2. Deferred deeplink/referrer delivery for uninstalled cases must be confirmed on a real clean device; unit tests can validate orchestration but not Android platform delivery.

7Run the tests

To confirm your checkout is healthy, run the unit-test suite (standard library only):

python3 -m unittest discover -s tests

All tests should report OK.

Troubleshooting

maestro: command not found

Maestro isn't on your PATH. Re-run the PATH export from step 2 and open a new terminal, then check maestro --version. Maestro also needs Java 17+ — verify with java -version.

adb devices shows nothing

The emulator isn't running or adb can't see it. Start an emulator from Android Studio's Device Manager, then re-run adb devices. If adb itself is missing, add the SDK platform-tools to your PATH (step 2).

"cannot proceed — no model configured"

AppPilot never guesses. Set APPPILOT_MODEL and APPPILOT_MODEL_API_KEY in your .env (see Configuration).

Login goals fail

Set APPPILOT_USERNAME and APPPILOT_PASSWORD. These are only needed for scenarios that actually sign in.

Wrong device targeted

Pass the exact id from adb devices via --device, e.g. --device emulator-5554.
